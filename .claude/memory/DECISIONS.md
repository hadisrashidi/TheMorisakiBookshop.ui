# Decisions
- 2026-10-24: Adding to the cart checks the CURRENT stock on the server first (`CartService.addCheckedToCart`: one `Books/GetBookById` call per click, because the list on screen can be old): stock 0 -> "ناموجود" toast, `in cart + wanted > stock` -> "فقط N عدد موجود است" toast, nothing added. `CartItem.stock` remembers the stock at add time so the `+` on the cart page stops there. The API still checks again at order time (another customer can buy the last copy in between). If the book call fails, nothing is added (the API helper shows why). Her request: say it at "add to cart", not at checkout.
- 2026-10-21: Checkout calls `Orders/PlaceOrder` (no more local fake orders; the old `morisaki-orders` localStorage key is deleted on start). Needs a login (guest goes to `/login?returnUrl=/cart`) and an address: the DEFAULT address (or the first) of the localStorage addresses page is the recipient; none -> `/addresses`; invalid mobile / postal code -> `/addresses` with a toast. The UI sends only book ids + quantities, never prices (API reads prices from the database). `OrdersService` keeps the loaded orders in a signal (`load()` on the orders page and the profile page); API date (UTC) is shown as Jalali, status code as Persian text (`OrderResponseModel.date/statusLabel/itemsCount` are filled client-side). Stock is taken at order time; no payment yet, status stays "در انتظار پرداخت". Her go-ahead ("do it as you suggested").
- 2026-10-19: The admin panel is NOT part of this storefront: it is the separate repo `TheMorisakiBookshop.admin.ui` with its own login (her request). The storefront only keeps the `apiImage` pipe: images uploaded in the admin panel are stored as `/uploads/...` on the API server, so every shop `<img>` of a book/author goes through the pipe; shipped covers (`/covers/...`) stay as they are.
- 2026-10-13: Every password input in the auth screens is `shared/components/password-field` (eye button shows/hides what was typed; `[(value)]` two-way signal). At login, an account without a name takes the name already saved in the local profile (`Auth/UpdateProfile` right after `startSession`, so the token is sent); the account menu shows "افزودن نام" while the account has no name. Her requests.
- 2026-10-13: Welcome toast = "<name> عزیز، خوش آمدید!" (plain "خوش آمدید!" when the account has no name); the account menu shows the name, falling back to the mobile. The name lives on the account (API `Users.Name`); `/register` asks for it and the profile page save sends it with `Auth/UpdateProfile`. The email of the last "remember me" login is kept in localStorage (`morisaki-last-email`) and pre-fills the email field; the PASSWORD is never stored by the app — the browser's password manager does that (login email field has `autocomplete="username"`). Her requests.
- 2026-10-13: After login / sign-up the UI goes to the home page (`/`), or back to `returnUrl` when the auth guard sent the person to login — not to the profile page. "Remember me" checkbox on `/login` (both tabs) and `/register` sends `rememberMe` → token lasts 30 days instead of 1 hour. Browser autofill of saved logins is NOT blocked: it is a browser feature that real users want, and on localhost it mixes in logins saved for other projects (her case) — fix by removing saved `localhost` logins in her browser. Her requests.
- 2026-10-13: Session = API token + user in localStorage key `morisaki-auth` (`shared/services/auth.service.ts`, session only, no HttpClient); API calls in `features/auth/services/auth.api.service.ts`; `core/interceptors/auth.interceptor.ts` adds the Bearer header to API calls and, on 401, logs out and goes to `/login`. localStorage is readable by any script on the page (XSS) — accepted for now, a cookie-based session would be the stricter alternative. Old fake-auth keys are deleted on start.
- 2026-10-13: `/register` = mobile + SMS code + email + password in one form (her test: email login on an SMS-only account failed and confused her). `/login` has SMS-code and email tabs and a link to `/register`; `/security` still adds email + password to an SMS-only account; password reset is `/reset-password` (SMS code). Supersedes "no separate register page" from earlier the same day.
- 2026-10-13: Dev only: when the API puts the code in `message` of `RequestOtp` (no SMS provider yet), the UI shows it as an info toast.
- 2026-10-12: `ApiHelperService` never throws: HTTP errors and `isSuccess: false` come back as an `ApiResponse` with `isSuccess = false` and a toast (`showErrorAlert`, default on) — components only check `result.isSuccess && result.data`. Alert types (Swal/redirect) not built; only what is used.
- 2026-10-12: Cart / liked / order models keep `price` as string for now (existing localStorage data), `Book.price` is a number — the conversion sits in `CartService.addToCart` / `LikedService.toggle`; revisit when cart moves to the API.
